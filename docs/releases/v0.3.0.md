# plat-operations v0.3.0

Adds an analyst entry point and a browser workbench to `boxscore-exact serve`,
lets `import_period` take file contents instead of a dataset, and makes
`issue_report` refuse a revision that a correction has superseded. It is
published to PyPI (`plat-operations`) and to GHCR
(`ghcr.io/paintbrushv/plat-operations`) as 0.3.0, the same way 0.2.0 was.

This release is `main` after v0.2.0 (commit `c2b2761`): PRs #28 to #34. Pull
request numbers below refer to
[paintbrushv/plat-operations](https://github.com/paintbrushv/plat-operations/pulls).
PRs #25 and #26 (OAuth introspection and the Keycloak-verified recipe) were
already in v0.2.0 and are not repeated here.

## What changed

### START_HERE.md and the `start_here` MCP prompt (PR #28)

- [START_HERE.md](../../START_HERE.md) is an entry point for an
  asset-management analyst with no context on the repository: what this is,
  three ways in (the firm's claude.ai or ChatGPT connector through IT, Claude
  Desktop, the container quickstart), the first three questions to ask with
  the answers from the synthetic sample, how to read and verify a citation,
  and what `review_required` means. README.md and QUICKSTART.md now point to
  it.
- The MCP server offers a second prompt, `start_here`, beside
  `boxscore_grounding`. It tells the model to call `describe` and then
  `list_revisions` with no filter, summarize what is loaded, offer the three
  questions word for word, and follow the grounding rule. It is served the
  same way over stdio and HTTP.
- The three questions are defined once (`START_HERE_QUESTIONS` in
  `boxscore/src/exact/mcp.rs`); a test fails if the fenced block in
  START_HERE.md differs from them.

### Browser workbench (PRs #29, #31, #32, #34)

`boxscore-exact serve` now also serves a page at `/` (with `/app.css`,
`/app.js` and `/workbench/auth.json`) on the same port, for analysts whose IT
has not approved an agent connection and for an IT reviewer who wants to see
the engine in a browser. It is built in four slices; see
[INSTALL.md, Browser workbench](../INSTALL.md#browser-workbench).

| slice | PR | what the page does |
|---|---|---|
| 1 | #29 | Lists what is loaded (`list_revisions`) and reviews a period (`review_period`): status and review reasons, the NOI bridge, every account, excluded and unmapped accounts, the correction's changes, and the citation line with a Copy button |
| 2 | #31 | Loads a period from files the user chooses, through a form built from `describe`'s adapter list; supports a correction behind a confirmation step; looks up a trace (`get_provenance`) |
| 3 | #32 | Issues a report from the review screen after a confirmation that shows the property, period, revision and review reasons; lists the reports already issued for the revision |
| 4 | #34 | Signs analysts in through the firm's identity provider (OAuth 2.1 authorization code with PKCE `S256`, the page as a public client) |

Security posture:

- The page and its two assets are compiled into the binary. Every response
  carries `Content-Security-Policy: default-src 'none'; script-src 'self';
  style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none';
  form-action 'none'; frame-ancestors 'none'`, plus `nosniff`, `no-referrer`
  and `no-store`. The page loads nothing from elsewhere, so the image still
  runs with `--network none` except for `serve`.
- Same-origin rule: the server refuses a request whose `Origin` header is not
  allowed. Its own origins are now allowed without `--allow-origin`: the
  origin of `--public-url`, the loopback spellings (`127.0.0.1`, `localhost`,
  `[::1]`) of a loopback public URL, and the loopback spellings on the bound
  port of a loopback bind. `--allow-origin` governs every other origin and is
  unchanged. Behind Docker port remapping or a proxy, give `--public-url` the
  URL the browser uses.
- Bearer-only authentication: the page sends its credential only as
  `Authorization: Bearer`, to the server it was served from. It uses no
  cookies and the server sends no CORS headers. Loading the page needs no
  token and shows no data; every data call goes to the authenticated
  `/v1/calc` routes, with the same origin check and rate limit as any other
  client. The page is not part of `/openapi.json`. An API key, or the access
  token from sign-in, is kept in the tab's `sessionStorage` only.
- No number is computed in the page. Every figure shown is the string an
  envelope carried; thousands separators are added by string manipulation, and
  money is never converted to a JavaScript number. Refusals show the engine's
  code and message as sent. The page builds its DOM with `createElement` and
  `textContent` only, and a test checks the source for `innerHTML`, inline
  handlers and `eval`.
- Browser sign-in (#34, new flag `--oauth-browser-client-id`): the page uses
  authorization code with PKCE `S256` and no client secret, with state, an
  `iss` check (RFC 9207) and `resource=<audience>` (RFC 8707). The code is
  removed from the address bar before anything else, the token is introspected
  by the server like any other bearer, and no refresh token is kept: after
  expiry the next request is not sent and the page asks to sign in again,
  never falling back to an API key. The page's CSP names the identity
  provider's token endpoint by exact URL in `connect-src`. The server refuses
  to start if the endpoint cannot be named that way, or if the issuer's
  metadata lists PKCE methods without `S256`. See
  [SECURITY.md](../../SECURITY.md) and
  [remote-mcp.md, Browser workbench sign-in](../connectors/remote-mcp.md#browser-workbench-sign-in).
- Signing out clears the tab's token and does not end the session at the
  identity provider. `sessionStorage` is shared by every page on the same
  origin and copied into a duplicated tab, so give the workbench an origin of
  its own.

### Calculation catalog

Three functions have new versions. Money, rounding and every other number are
unchanged. Versioning follows [docs/EXACT_CENTS.md](../EXACT_CENTS.md).

| function | was | now | PR | change |
|---|---|---|---|---|
| `describe` | 1.1.0 | 1.3.0 | #30, #33 | The listing changed twice: 1.2.0 (#30) for `import_period`'s new input and the adapter description, 1.3.0 (#33) for `issue_report`'s refusal |
| `import_period` | 1.0.0 | 1.1.0 | #30 | Takes an adapter profile with the files' contents inline, as an alternative to `dataset` |
| `issue_report` | 1.0.0 | 1.1.0 | #33 | Refuses a revision that a correction has superseded |

The other nine functions (`noi_variance`, `review_period`, `list_revisions`,
`occupancy`, `economic_occupancy`, `delinquency`, `t12`, `close_readiness`,
`get_provenance`) are unchanged at 1.0.0.

### `import_period@1.1.0`: inline files through an adapter (PR #30)

- `import_period` takes exactly one of `dataset` (a canonical period dataset)
  or `profile` with `files` and `options`. With `profile`, the server runs the
  registered source adapter (`canonical.csv/1`, `canonical.json/1`; see
  `describe`) on the file contents sent in the call, each file's full text as
  a JSON string. It goes through the same path as `boxscore-exact import-with`,
  so the same bytes give the same dataset, the same `input_sha256` and the same
  per-file hashes. This is also what lets an agent import a pasted export over
  MCP, and what the workbench's import form uses, since a page cannot hand the
  server a path.
- Both or neither of `dataset` and `profile`, `files` or `options` beside
  `dataset`, or an explicit `null` for any of those keys refuse with
  `INVALID_INPUT`. An unknown profile refuses `UNKNOWN_PROFILE`. Files and the
  request body are capped at 2 MiB, escaping included.
- `sources.supplied`: a caller's own `sources` object is recorded under
  `sources.supplied` and nowhere else; it is stored as sent and is not
  verified. Every other key of a revision's `sources` (`profile`, `files`, the
  per-file hashes, `canonical_json_sha256`) is written only by the server, and
  each inline file is recorded as name, SHA-256 and bytes with `inline: true`.
- A dataset's `property` must have no leading or trailing whitespace (1 to 120
  characters), like account codes, so `Probe ` and `Probe` cannot become two
  property series.

### `issue_report@1.1.0`: a superseded revision is refused (PR #33)

- If any stored revision names the revision as its parent, `issue_report`
  (and `boxscore-exact issue`) refuses with `SUPERSEDED`, and the message
  names the latest revision of the chain by id and revision number. There is
  no override; issue the latest revision instead.
- The successor check, the review and the insert of the report run in one
  immediate SQLite transaction, so a correction committed by another
  connection cannot land between the check and the insert, and a cancelled
  request rolls back.
- Unchanged: issuing the latest revision again makes another report, and a
  `review_required` revision still issues with its reasons visible. A cyclic
  revision chain refuses `INTEGRITY_ERROR`. Before this release the engine
  issued any existing revision, after which `t12` with
  `revision_policy: issued_only` could report a superseded revision's
  figures.

### HTTP API response headers (PR #29)

Every `/mcp` and `/v1/calc` response, including authentication refusals, now
carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, so a
browser or proxy does not cache an envelope.

### New `serve` flag (PR #34)

`--oauth-browser-client-id <id>`: the public OAuth client IT registers at the
identity provider for the workbench page, with the redirect URI exactly
`<public-url>/`. It needs the OAuth options already required by `serve`.
Start-up discovery then also reads the issuer's `authorization_endpoint` and
`token_endpoint` from its RFC 8414 metadata (https, or http for a loopback
host). The server's own outbound connections are unchanged; the analyst's
browser additionally talks to the identity provider to sign in. The example
realm file [keycloak-realm.example.json](../connectors/keycloak-realm.example.json)
gains a `boxscore-workbench` client.

### CI (PRs #28, #34)

The Rust job in `ci.yml` has a new step, `node --test
scripts/workbench_unit_test.mjs`, which runs unit tests of the page's pure
sign-in logic (token state, callback classification, authorize parameters) on
the runner's Node with its built-in test runner, with no npm and no
dependencies. CI also runs when `START_HERE.md` or that script changes. The
image check (`scripts/check_image.py`) now also fetches the workbench page and
its Content-Security-Policy and checks that `/v1/calc/describe` answers the
server's own origin and refuses another.

## Publishing

On a `v*` tag, `release.yml` runs the version gate (the tag must equal the
version in `pyproject.toml` and `boxscore/Cargo.toml`, and the version must not
already be on PyPI), the wheels and sdist, the Rust tests (which include the
node step above) and the image build.

- PyPI: `plat-operations==0.3.0`. The `wheels.yml` matrix builds wheels for
  Linux x64 (`x86_64-unknown-linux-gnu`, manylinux 2_28), macOS Intel
  (`x86_64-apple-darwin`), macOS Apple Silicon (`aarch64-apple-darwin`) and
  Windows x64 (`x86_64-pc-windows-msvc`), plus an sdist rebuilt in isolation.
  Each wheel is installed and checked with `scripts/check_native.py` on Python
  3.12 and 3.11. The package requires Python 3.11 or later.
- GHCR: `ghcr.io/paintbrushv/plat-operations:0.3.0` and `sha-<7 hex>`
  (`linux/amd64`; there is no `latest` tag), signed with cosign keyless
  signing, with the image SBOM attached as a signed attestation. To verify, see
  [Verify the image](../INSTALL.md#verify-the-image) and
  [DATA_FLOW.md](../DATA_FLOW.md#8-how-to-verify-the-image).

GitHub Actions stay pinned to the commit SHAs set for v0.2.0, and the
Dockerfile base image digests are unchanged.

## Known limitations

- The workbench has not been run in a real browser. It was driven end to end
  with the page's own `app.js` under jsdom against a live server, with a fetch
  shim imitating the CSP and CORS checks. Layout at phone width, colours and
  clipboard copy are unverified, and so is a real browser's own CORS and CSP
  enforcement.
- Browser sign-in is verified only against Keycloak 26.0.8. Okta was not tried
  (whether its token endpoint answers a browser origin is unverified), and
  Microsoft Entra ID and Auth0 cannot be used because they offer no token
  introspection.
- Sign-in from the claude.ai and ChatGPT connectors has not been tried with a
  real account; their walk-throughs in
  [remote-mcp.md](../connectors/remote-mcp.md) are marked unverified. The
  server side was checked against Keycloak.
- UPL-102 is open: the engine accepts byte-order-mark and other invisible
  format characters in categories.
- A byte-order mark in a JSON file (a snapshot, say) is refused on every
  import path.
- An import from the page that times out (60 seconds), and an issue that fails
  without an answer, may already have been stored on the server; the page says
  so and asks the user to reload the list before trying again.
- The legacy `boxscore` commands still store money as `f64`.

## Upgrading from 0.2.0

- No schema change. The exact-cent database schema version is still 2
  (`SCHEMA` in `boxscore/src/exact/mod.rs` and `docs/EXACT_CENTS.md` are
  unchanged since v0.2.0, and `boxscore/src/exact/store.rs` has no schema
  statement changes). A 0.2.0 database opens unchanged with 0.3.0, and no
  migration is needed.
- Catalog versions that moved: `describe` 1.1.0 to 1.3.0, `import_period` 1.0.0
  to 1.1.0, `issue_report` 1.0.0 to 1.1.0. A client that pins one of these with
  `version` gets `VERSION_MISMATCH` until it pins the new version. The
  `describe` output carries `producer.version` 0.3.0, so its `output_sha256`
  differs from 0.2.0's.
- Two behaviors differ for callers that were working before. `issue_report`
  refuses a superseded revision (`SUPERSEDED`). And `import_period` now records
  a caller's `sources` under `sources.supplied`, where 0.2.0 recorded it as the
  whole `sources` value; the server-computed keys are now always present, and a
  dataset with leading or trailing whitespace in `property` is refused.
- The workbench is new and is on the same port as the API: `serve` now
  answers `GET /` with the page, and prints `workbench at <public-url>/` at
  start-up. Nothing needs enabling, and it holds no data until a request
  carries a valid bearer token. Requests from the page carry an `Origin`
  header that the server's own origin satisfies; if the server is reached
  through a remapped port or a proxy, pass `--public-url` (or
  `--allow-origin`) with the URL the browser uses.
- Browser sign-in is off unless `--oauth-browser-client-id` is given.
